# 一个人写、工具检查、独立上下文审查

日常只需给五字段任务。Agent 在边界内连续做完，不要求你逐步批准；确定性操作交给脚本。
本仓库准备了一次较完整的流程，普通小改动只运行相关测试，不机械地全仓库跑一遍。
Gemini-only 流程目前完成了脚本、真实配置加载器和权限引擎验证；在线调用被个人版客户端停服限制阻断，未冒称线上运行成功。当前可先使用已验证的 Codex 独立审查方式。

## Plan → Implement → Test → Review → Commit

1. **需求**：给出目的、范围、验收。已清楚的小任务直接做；复杂任务先 3 步计划。只有影响选择的缺失信息才提问。
2. **实现**：Agent 先读相关代码/测试/STATUS，做一个可回退的小改动。重要依赖、破坏性命令、核心接口和凭证操作需要确认；这是风险边界，不是每步审批。
3. **检查**：语法/编译/类型检查（项目有才用）→核心单测→相关集成→必要的运行或浏览器验证。失败修复；没有通过就不包装成成功。
4. **审查**：新会话或只读子代理，只给任务、规则、diff、相关源码与测试证据。不传实现者的长聊天和“为什么这样做正确”的解释。
5. **修复**：实现 Agent 复现有依据的问题后修复、重跑受影响测试。纯风格意见不进入循环。争议只在影响需求或风险时让人判断。
6. **最终验证与提交**：核对 diff/范围/无凭证，保存本地 Git 提交，更新 ≤15 行 STATUS。发布、push 和远端保护按任务授权另做，不自动扩张。

一般只需人给一次任务；遇到一个真正的高风险/阻塞选择再介入。没有缺陷时，不为完成“Review 仪式”反复调用模型。
工具沙箱的原生审批可能仍然出现，AGENTS.md 无法替你取消它；不要用 YOLO 绕过。

## 本仓库的自动命令

```powershell
npm run workflow:verify
npm run review:pack
npm run review:gemini -- SAME_MODEL_ID
```

- verify 顺序运行原样例检查/测试/浏览器、练习检查/测试/浏览器、规则和审查脚本测试；记录到被忽略的 artifacts/workflow/validation.json。
- pack 从 Git 相对 HEAD 的改动和新文件收集证据，执行 Scope 检查、敏感路径拒绝、有限凭证特征检查，包含源码与 diff。
- 文件或任务在测试后变化，摘要不同即拒绝打包；审查前再次核对摘要。修复后重新验证/打包。
- review:gemini 启动不带 resume 的新进程，用与实现相同的显式模型；stdin 输入 packet，JSON 输出保留 stats（token/耗时信息）。
- CLI 显式传 `.gemini/review-policy.toml`，当前规则禁止所有工具；审查只看 packet，不能 shell、修改文件或读取凭证。

认证可用后，`npm run qa -- SAME_MODEL_ID` 可一次顺序执行 verify → pack → 独立 Review。当前按用户要求暂缓在线部分，先运行相关客观检查即可。

默认任务 tasks/preparation.md 是本轮准备。后续小任务复制五字段 Markdown，再执行：

```powershell
npm run workflow:verify -- tasks/my-task.md
npm run review:pack -- tasks/my-task.md
npm run review:gemini -- SAME_MODEL_ID
```

这个仓库的 verify 脚本是演示用固定检查集合；换 Python/Web 仓库时替换为该项目的必要检查，不引入第二套任务调度框架。
当前 packet 上限 220KB；日常应远小于此，一两个文件通常就够。超过上限拆任务，不继续塞整仓库。
Scope 之外的无关未提交改动会阻止打包；先保存另一项工作的提交或使用独立 checkout，不把别人的改动偷偷加进任务。
规则文件和脚本存在不代表绝对安全：敏感路径/特征过滤不是完备的 Secret 扫描，也不是操作系统沙箱。

## Gemini-only：三层证据

**第一层：客观工具。** 测试、运行、边界输入与失败注入比“模型认为没问题”更可靠。本练习只用已有 Node 语法检查、Python AST/unittest、JS 测试和 Playwright；没有为展示增加 Linter 或类型系统。

**第二层：独立上下文。** 默认推荐新的 headless Gemini 进程，明确同一个 MODEL_ID，关闭工具；最少管理成本且容易记录输入输出。手动新会话也可：退出旧 CLI，重新启动、不加 --resume，只附任务/diff/测试。已配置的 qa-reviewer 使用独立上下文、继承主模型，只有读取/搜索工具，不拥有 shell 或编辑工具。它不能自己重跑测试，必须注明证据由脚本提供。[官方子代理说明](https://geminicli.com/docs/core/subagents/)

**第三层：缺陷标准。** 只报 P0/P1/P2（阻断/严重/一般）且给出 file:line、原因、复现或验证方法。检查验收、逻辑、边界、异常、游戏状态竞态、范围、凭证、核心测试。没有证据不报，不用长篇风格建议制造工作。

独立上下文能减少“为刚写的代码辩护”，但同模型仍可能有相同盲点，也可能误报。它不等于独立模型、不替代测试或队友判断，模型的“没有发现”不证明没有缺陷。

## 为什么不用 worktree 做每次 Review？

只看 diff 和相关代码时，新会话 + 无工具 packet 更简单。worktree 适用于需要独立运行旧/新版本、同时保持两份状态的调试；它只隔离工作目录，不隔离权限、网络或凭证。
三人各自 clone 通常已经足够。不要让多个写 Agent 同时改同一个目录，避免以协调 Agent 取代实际开发。

## 单 Agent、Subagent、新会话怎么选？

| 场景 | 选择 | 切换时只交接什么 |
| --- | --- | --- |
| 单个小 Bug/功能，背景仍相关 | 一个 Agent 连续实现与测试 | 不切换；完成时简报 + STATUS |
| 一个独立的只读审查/调查，主任务还要继续 | 一个只读 Subagent | 明确问题、文件、证据，结果短回传 |
| 完成一任务后进入新任务；聊天已扩张；要独立审查 | 新会话 | AGENTS + STATUS + 当前任务；审查加 diff/测试 |
| 两个互不重叠模块必须并行 | 人先划定文件范围，再两 Agent/两个 checkout | 契约与各自 Scope；一个负责人集成 |

每个任务 20–60 分钟左右是检查边界的提醒，不是强制计时器。遇到范围持续增加就拆出下一任务。不要反复复制整份黑客松需求。

## 调用、上下文和成本控制

- 不在每帧调用模型；按回合/关键事件调用，输入只包含必要状态，输出只包含有限决策。
- 一次实现、一次有针对性的审查为默认；只有新改动/失败/具体担忧才复验或再审。
- 测试用 Mock，真实请求单独标记；不让测试自动继承 live 凭证。
- API 设置有界超时、显式错误与退路；对可幂等的确定性输入才考虑缓存，键包含状态/模型/提示版本，错误不缓存。
- Headless JSON 会提供统计，可比较输入大小、token 和延迟；不凭感觉堆上下文。[官方 Headless 说明](https://geminicli.com/docs/cli/headless/)
- 若真实审查发现 >3 个独立大问题，先排序修复，不开无限递归 Agent 链。

## 交接状态模板

```text
目标 / 当前分支与提交：
已完成：
已验证（命令 + 结果）：
未验证 / 阻塞：
下一步（最多 3 条）：
```

可读状态是交接入口，测试 JSON 是证据；两者不互相伪装。不要把整段聊天写进 STATUS。
